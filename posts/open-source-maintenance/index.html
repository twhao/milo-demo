一个开源项目，怎样才能让陌生人放心使用

把代码上传到 GitHub，只是开源项目的起点。陌生人需要判断的不仅是“能否下载”，还有“是否容易理解、能否持续维护、遇到问题怎么办”。

一份 README 应该回答什么

最有用的 README 不一定最长，但应该让使用者迅速找到：

  1. 这个项目解决什么问题。
  2. 适用于什么环境，有哪些已知限制。
  3. 如何安装、运行，以及如何卸载。
  4. 在哪里查看真实效果。
  5. 出现问题时如何反馈。

演示站正好补上了文字文档不擅长的一环：让访问者在安装之前亲自感受界面和交互。

版本号是沟通方式

例如，v1.2.3 经常被解释为“主版本号.次版本号.修订号”。不过具体是否遵循语义化版本规则，仍然要由项目维护者明确说明。

  • 修订版本通常用于兼容性修复。
  • 次版本通常表示向后兼容的功能增加。
  • 主版本可能表示存在破坏性变更。

不要只发布标签而不解释变化。对于安装者来说，一份具体的变更记录比“优化体验”更有帮助。

区分演示站与实际产品

演示站可以展示多个功能，但应当标明版本；开发分支中尚未发布的实验特性，不应被默认为稳定版本已经支持。

材料 主要作用
README 帮助新人开始使用
Demo 展示实际外观与交互
CHANGELOG 解释版本变化
Issues 集中记录问题与需求
Release 提供明确的发布节点

把可信度建立在事实之上

公开已知问题、验证环境和测试范围，不会削弱项目的专业程度。相反，它能让使用者判断自己是否适合使用。

好的开源维护，不是声称“没有问题”，而是让问题变得可发现、可讨论、可修复。

项目规模可以很小，但文档、版本和反馈机制值得从一开始就认真对待。

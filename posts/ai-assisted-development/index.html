AI 能写代码之后，开发者更应该验证什么

生成代码的成本在下降，但判断代码是否符合目标，仍然需要可靠的方法。能运行，只是完成工作的第一层。

先写清楚验收标准

例如，要求“修好首页图片”太模糊。更可验证的需求是：

  • 首页图片容器采用 16:10 比例。
  • 图片使用 cover 时可以裁切，但不能被拉伸变形。
  • 使用 contain 时应该完整显示原图。
  • 桌面与手机端表现一致。
  • 文章正文中的图片不受首页封面规则影响。

这样一来，无论由人还是 AI 编写代码，结果都有明确的检查依据。

把验证拆成四层

层级 要回答的问题
语法检查 代码是否能正确解析？
自动化测试 已知功能是否仍然符合预期？
浏览器检查 在真实页面和不同屏幕上是否正常？
人工验收 交互、文字和视觉体验是否真的合适？

自动化测试能防止回归，却不能代替对体验的判断；人工目测能发现细节，也不能代替稳定、可重复的测试。

学会检查“没有改动”的部分

修改一个 CSS 规则后，不只检查目标卡片，还要看导航栏、文章正文和深色模式。修复某个页面时，最好也打开原本正常的页面。

这叫回归检查。它的核心不是追求测试数量，而是控制“解决一个问题，却制造另一个问题”的风险。

保持可追溯

一项功能完成后，最好能够回答：

  1. 为什么要改？
  2. 具体修改了哪些文件？
  3. 用什么方式验证？
  4. 如果出问题，能退回哪个版本？

Git 提交、测试记录和版本说明，是回答这些问题的基础。

AI 可以加速实现，但不能替人承担未被验证的假设。

更成熟的工作流不是“提要求 → 接受结果”，而是“定义目标 → 实现 → 验证 → 记录 → 发布”。
